Lab 1 · Business track · 90 min

Ghost Providers: build a directory agent

No SQL needed. You describe the business; Cortex Code builds it.

Download Lab 1

The problem

Members call doctors listed in the Triple-S directory and get turned away: the contract ended or the credential expired, but the record is still published. That means complaints, appeals and risk in CMS directory audits. Today, finding them requires an IT ticket.

What you build

A semantic view with the business definition of "active provider", and a Cortex Agent in CoWork that your team can ask questions in Spanish.

The result

The real count of ghost providers and a cleanup list ranked by member complaints, on the same day.

The "aha" moment The obvious answer finds only 1 in 3 ghost providers. Then the AI gives a wrong number even though the SQL runs fine. Lesson: fix the semantic view, not the prompt.

Step by step

  1. Set up. Run the first two cells (setup_session, load_data). You'll see 2,000 synthetic providers.
  2. Explore the data with Cortex Code: 
    I'm a business analyst on the Triple-S Network team. Look at the tables in my schema TSS_SNOWDAY.LAB1. For each table, explain in plain English what it represents, what one row means, and how the tables connect to each other.
  3. Define "active provider" in business words: 
    A provider is ACTIVE only if: contract status is ACTIVE, effective date <= today, termination date is empty or >= today, and the credential is ACTIVE and not expired. A GHOST provider is published but NOT active. Count ghost providers by reason and compare with the naive count.
  4. Watch it fail, then fix the model. Ask the v1 semantic view a question and write down the number. Then have Cortex Code update the semantic view (section 4.3) and ask the same question again.
  5. Create the agent (sections 5 and 5.1). The notebook makes it visible in CoWork.
  6. Test it in CoWork: open Triple-S Directory Accuracy Assistant and ask: 
    ¿Cuántos proveedores fantasma tenemos y por qué razón?
    Cardiología en Bayamón: ¿hay proveedores fantasma?
  7. Act. Build the cleanup worklist and see how many complaints come from ghost providers.

Lab 2 · Technical track · 90 min

Protect, classify and enrich Medicare appeals

For people who write SQL. Cortex Code writes most of it; you validate it.

Download Lab 2

The problem

Expedited Medicare appeals have a 72-hour deadline. Upheld or late cases go to the IRE, and IRE overturns signal wrong denials. Nobody measures overturns by reason, because the reason is free text full of PHI.

What you build

A pipeline: redact PHI, classify each appeal with AI, flag weak denial reasons, and run it in an incremental Dynamic Table.

The result

Live SLA tracking, today's at-risk appeals, and the IRE overturn rate by appeal category.

BRONZERaw appeals + masking
→
SILVERAI_REDACT + safety net
→
ENRICHEDAI_CLASSIFY · AI_FILTER · AI_EXTRACT
→
GOLDSLA + overturn rates
The "aha" moments 1. AI_REDACT misses the Medicare ID (MBI). The leak report catches it. Always validate AI output.
2. Denials with a vague reason are overturned by the IRE about 4x more often.
3. With incremental processing, each appeal goes through AI once.

Step by step

  1. Set up. Run the first two cells (setup_session, load_bronze): 300 appeals plus 20 new ones for later.
  2. Estimate cost first: 
    Before I run AI_REDACT and AI_CLASSIFY on APPEAL_REASON_TEXT, estimate how many tokens that would consume for the whole table using AI_COUNT_TOKENS.
  3. Protect PHI. Apply masking, prototype AI_REDACT on 5 rows, build SILVER and read the leak report. Then fix it: 
    AI_REDACT is not catching the MBI. Update SILVER_APPEALS so that after AI_REDACT a REGEXP_REPLACE pass replaces any MBI pattern with [MBI], any 787 phone with [PHONE_NUMBER] and any MM/DD/YYYY date with [DATE]. Then re-run the leak report.
  4. Classify and enrich. Prototype on 10 rows, then: 
    Turn the prototype into an incremental Dynamic Table ENRICHED_APPEALS on top of the SILVER_APPEALS table. Keep the AI functions in the SELECT clause so it stays incremental.
  5. Validate. Compare the AI category with the human one. Read the disagreements and decide who is right.
  6. Go incremental. Add the 20 new appeals, refresh, and check REFRESH_ACTION = INCREMENTAL and ROWS_INSERTED = 20.
  7. GOLD. Build the SLA and overturn views, and look at today's at-risk queue.

Keep in mind
  • The MBI leak is expected. It is the lesson of section 2. Don't skip the leak report.
  • SILVER is a regular table. In our tests AI_REDACT failed on incremental Dynamic Table refreshes, while the other AI functions worked. The notebook explains the design.
  • Building SILVER and ENRICHED takes 1 to 3 minutes each.
  • The AI agreed with the human label about 79% of the time in our run. Section 4.1 shows how to improve it.

Open your lab in Snowflake

Everything is inside the notebook. There is no other code to run.

  1. Claim your account at go.dataops.live/triple-s-snowday/register and log in to Snowsight.
  2. Download your lab notebook: Lab 1 or Lab 2.
  3. In Snowsight, go to Projects » Workspaces → + Add New → Upload Files, and choose the .ipynb file.
  4. Open the notebook and connect it with the compute pool SYSTEM_COMPUTE_POOL_CPU. The first start takes 1 to 2 minutes.
  5. Run the first cell. It switches to ACCOUNTADMIN, creates the warehouse TSS_SNOWDAY_WH, turns on cross-region AI and creates your lab schema.
  6. Open Cortex Code (icon in the lower-right corner) and follow the notebook. Each section has a prompt to paste, and a reference cell if you fall behind.
