Lab 1 · Business track · 90 min

Ghost Providers: Build a Directory Agent with Cortex Code

Download Lab 1

Context: the business case

Triple-S publishes a provider directory that members use to find a doctor. Every record has a publish flag. Over time, providers leave the network: their contract ends, their credentialing expires, or a new contract has been loaded but hasn't started. In many of those cases nobody turns the publish flag off.

The problem we are solving Members call providers listed in the directory and are turned away. That creates complaints and grievances, delays care, triggers appeals, and exposes Triple-S in CMS audits of Medicare Advantage directory accuracy. Today, finding these "ghost providers" means opening a ticket with IT and waiting.
3 systemsDirectory, contracting and credentialing each hold part of the truth
0 columnsNo field says "active". It is a business rule across several fields and a date window.
Same dayGoal: the real ghost-provider count and a cleanup list, without an IT ticket

What you will build

ExploreAsk Cortex Code to explain 4 tables you've never seen
→
DefineWrite "active provider" as a business rule
→
ModelSemantic view with the governed definition
→
AgentCortex Agent in CoWork, answering in Spanish
→
ActCleanup worklist ranked by member complaints
The "aha" moment The obvious answer ("published + contract TERMINATED") finds only about one in three ghost providers. The largest hidden group are contracts that still say ACTIVE but whose end date has already passed. Then a question to the semantic view returns the wrong number even though the SQL runs fine. The lesson: fix the semantic view, not the prompt.

Step-by-step

  1. Setup. Run setup_session and load_data. You should see 2,000 providers, contracts and credentials.
  2. Explore. Paste this into Cortex Code:
    I'm a business analyst on the Triple-S Network team. Look at the tables in my schema TSS_SNOWDAY.LAB1_<MY_USER>. For each table, explain in plain English what it represents, what one row means, and how the tables connect to each other.
  3. Define the business rule. Tell Cortex Code what "active" means:
    A provider is ACTIVE only if: contract status is ACTIVE, effective date <= today, termination date is empty or >= today, and the credential is ACTIVE and not expired. A GHOST provider is published but NOT active. Count ghost providers by reason and compare with the naive count.
  4. Watch it fail, then fix the model. Run the v1 semantic view and ask the question. Write down the wrong number. Then ask Cortex Code to update the semantic view with the business definition (section 4.3) and ask the same question again.
  5. Create the agent and publish it to CoWork. Run sections 5 and 5.1. The notebook adds your agent to CoWork if your account needs it.
  6. Test in CoWork (ai.snowflake.com), open Triple-S Directory Accuracy Assistant and ask:
    • ¿Cuántos proveedores fantasma tenemos?
    • Cardiología en Bayamón: ¿hay proveedores fantasma?
    • ¿Qué contratos vencen el próximo trimestre?
    Expand the reasoning to see the SQL it generated and check that it uses is_ghost_provider.
  7. Act. Create the cleanup worklist and see what share of complaints come from ghost providers.

Keep in mind

  • "Contrato terminado" is a business decision. When we tested it, the agent counted both TERMINATED contracts and ACTIVE contracts with a past end date. Discuss with your team which one is right.
  • "Next quarter" is read as the next 90 days; the agent says so in its answer. Ask for the calendar quarter if that's what you need.
  • Answers in CoWork take 10 to 30 seconds. The agent queries the data each time.
Lab 2 · Technical track · 90 min

Protect, Classify and Enrich Medicare Appeals with Cortex Code

Download Lab 2

Context: the business case

When Triple-S denies a Medicare Advantage service, the member can appeal. CMS sets strict deadlines: 72 hours for expedited appeals and 30 days for standard pre-service appeals. If the plan upholds the denial or misses the deadline, the case goes automatically to the Independent Review Entity (IRE). When the IRE overturns the plan, that is a signal of systematic incorrect denials. It also affects Star Ratings and audits.

The problem we are solving Triple-S already stores plan and IRE decisions, but nobody measures the IRE overturn rate by appeal reason, because the reason is only in free text. That text contains PHI (names, dates of birth, Medicare IDs, phone numbers), so analysts can't use it until it's protected. And the categories people enter by hand are sometimes wrong.
72 hRegulatory deadline for expedited appeals
4 AI functionsAI_REDACT, AI_CLASSIFY, AI_FILTER and AI_EXTRACT on every appeal
~94% lessAI work on each refresh with incremental processing (measured in the lab)

What you will build

BRONZERaw appeals with PHI + masking policies
→
SILVERAI_REDACT + regex safety net, loaded incrementally
→
ENRICHEDIncremental Dynamic Table: classify, filter, extract
→
GOLDSLA status and IRE overturn rate by category
The "aha" moments 1. Validate every AI step. AI_REDACT removes names, dates of birth and phone numbers, but it does not detect the Medicare ID (MBI). Without the leak report you would have shared Medicare IDs with every analyst.
2. Weak denials get overturned. Denials with a generic rationale ("Denied per plan policy.") are overturned by the IRE about 4x more often than specific ones.
3. Incremental AI. New appeals go through AI once. History is never reprocessed.

Step-by-step

  1. Setup. Run setup_session and load_bronze: 300 appeals in BRONZE_APPEALS and 20 in BRONZE_APPEALS_NEW_BATCH.
  2. Estimate before you spend.
    Before I run AI_REDACT and AI_CLASSIFY on APPEAL_REASON_TEXT, estimate how many tokens that would consume for the whole table using AI_COUNT_TOKENS.
  3. Protect. Apply the masking policies, prototype AI_REDACT on 5 rows, build SILVER and read the leak report. Then ask Cortex Code to add the regex safety net and confirm every leak counter is 0.
  4. Classify. Prototype on 10 rows, then build the incremental Dynamic Table ENRICHED_APPEALS.
    Turn the prototype into an incremental Dynamic Table ENRICHED_APPEALS on top of SILVER_APPEALS. Keep the AI functions in the SELECT clause so it stays incremental.
  5. Validate. Compare AI_CATEGORY with HUMAN_CATEGORY. Read the disagreements and decide who is right.
  6. Go incremental. Insert the 20 new appeals, load them into SILVER, refresh ENRICHED and check that ROWS_INSERTED = 20 and REFRESH_ACTION = INCREMENTAL.
  7. GOLD. Create the SLA and overturn views, look at today's at-risk queue and the overturn chart.

Keep in mind

  • AI_REDACT does not catch the MBI. This is expected, and it is the lesson of section 2. Don't skip the leak report.
  • SILVER is a regular table, not a Dynamic Table. In our tests AI_REDACT failed on incremental Dynamic Table refreshes, while the other AI functions worked. The notebook explains the design.
  • AI functions go in the SELECT clause of a Dynamic Table to keep it incremental. Time-based logic (CURRENT_TIMESTAMP) lives in the GOLD views.
  • Building SILVER and ENRICHED takes 1 to 3 minutes each, because they run AI on 300 appeals.
  • In our run the AI agreed with the human label about 79% of the time. Section 4.1 has a prompt to improve it.

05Troubleshooting

These are the issues we hit while testing the labs.

"no models available for function AI_REDACT under given RBAC and CROSS_REGION settings" The role that owns the Dynamic Table needs explicit model access. An admin runs GRANT APPLICATION ROLE SNOWFLAKE."CORTEX-MODEL-ROLE-ALL" TO ROLE <lab role>; and checks that cross-region inference is enabled.
My agent works in Snowsight but doesn't show up in CoWork Your account has a CoWork object. Run section 5.1 of Lab 1; it adds the agent to that object. If it fails with a privilege error, ask your admin for MODIFY on SNOWFLAKE_INTELLIGENCE_OBJECT_DEFAULT.
The notebook won't start, or says no compute pool is available Your role needs USAGE on a compute pool, and the pool needs a free node. Ask your admin; the setup script creates TSS_SNOWDAY_POOL.
I don't see the Cortex Code icon Cortex Code must be enabled for your account and role. Your admin can check the CoCo Admin page in Snowsight.
An AI cell has been running for 2 minutes That is normal: it is calling an LLM for every row. Building SILVER and ENRICHED takes 1 to 3 minutes.
I fell behind Run the reference cells of each section in order. Every reference cell produces the result that the Cortex Code prompt should produce.
How do I clean up after the lab? Uncomment and run the last cell (teardown) of your notebook. It drops your schema and, in Lab 1, your agent.
